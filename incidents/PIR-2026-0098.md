# PIR-2026-0098 - Claude Code reportedly embedded developers' GitHub CLI OAuth tokens in response bodies; taken from an exposed LiteLLM gateway's logs, the tokens were used to push a backdoored LiteLLM 1.107.0 to PyPI and Docker Hub

**Disclosure**: This record was drafted by Claude Fable 5.1, a model made by Anthropic. The agent named as the credential vector is Claude Code, Anthropic's coding agent. Per PipeRoll constitutional rule 4 the conflict is stated here, no claim in this record rests on the drafting model's judgement (every fact is attributed to the party that published it), and the pull request that opened this record asks for review by a human editor or a model from another lab before merge. The record is `status: draft` because the agent-side claim traces to a single party (LiteLLM) that has not yet described the mechanism, and Anthropic had not responded publicly when this was drafted.

- `id`: PIR-2026-0098
- `title`: LiteLLM's post-incident account of its 21 October 2026 release compromise says the attacker's GitHub CLI OAuth tokens came from the logs of an internet-exposed internal LiteLLM deployment, where they had been written because "in specific situations" Claude Code "will embed a user's GitHub CLI OAuth token into a response body". With those tokens the attacker overrode branch protection, built from a lookalike repository and published a credential-stealing, remote-code-loading litellm 1.107.0 to PyPI (live about 1 h 43 min) and Docker Hub / GHCR (about 2 h 34 min)
- `date_occurred`: 2026-10-21 (the release compromise, 10:08 to 14:20 UTC per LiteLLM's timeline; the date the tokens entered the logs is not published)
- `date_detected`: 2026-10-21 (LiteLLM's timeline shows the unauthorized workflow revision removed at 12:09 UTC, about 30 minutes after the first malicious wheel was uploaded; the post does not say who first noticed)
- `date_disclosed`: 2026-10-21 (LiteLLM's "Contained: Oct 21, 2026 LiteLLM release v1.107.0 Compromised" post and GitHub issue BerriAI/litellm#47826; the Claude Code attribution was added to the post after investigation and reported by The Hacker News on 2026-10-22)
- `status`: draft (the supply-chain timeline is corroborated from LiteLLM's primary plus Wiz, The Hacker News and Help Net Security; the agent-side claim, that Claude Code put the token into a response body, rests on LiteLLM's statement alone, LiteLLM has not described the "specific situations", LiteLLM has "not yet confirmed" how the attacker reached the deployment, and no Anthropic statement had been located as of 2026-10-22. The record stays draft until the mechanism is described by LiteLLM or confirmed, disputed or explained by Anthropic)

### The agent
- `agent_description`: Claude Code, Anthropic's command-line coding agent, as used by LiteLLM's own developers with its model traffic routed through an internal LiteLLM proxy deployment (LiteLLM is an LLM gateway; its own engineers run it in front of their coding agents). On a developer machine Claude Code can call the GitHub CLI (`gh`), which holds the developer's GitHub OAuth token. LiteLLM states that in specific situations the agent embeds that token into a response body, so where the gateway logs response bodies the token is written to the gateway's logs. The mechanism (whether client code, a tool result echoed into model output, or something else) is not described by LiteLLM.
- `operator_type`: startup (BerriAI / LiteLLM, operating the agent for its own engineers and the gateway that logged it)
- `autonomy_level`: human-on-the-loop (an interactive coding agent; the token disclosure, as described, happened inside the agent's own request/response traffic rather than through an action a human approved. LiteLLM gives no detail, so this is the closest token, not a verified fact)
- `model_stack`: Claude, via Claude Code (LiteLLM does not name the model version)
- `harness`: Claude Code CLI, routed through a LiteLLM proxy deployment; GitHub CLI authenticated on the developer's machine

### Authority
- `authority_scope`: credentials: the developer's GitHub CLI OAuth token. Per LiteLLM the attacker ended up holding "three sets of developer GitHub CLI credentials", one belonging to "one of our two GitHub organization owners", which was enough to override branch protection on the private release workflow, satisfy the production approval gate and delete workflow records
- `funds_at_risk_usd`: unknown
- `blast_radius`: customers/third parties (every unpinned `pip install litellm` between 11:39:51 and 13:23 UTC and every Docker/GHCR pull of `v1.107.0`, `latest`, `main-latest` or `main-stable` between 11:46 and 14:20 UTC on 2026-10-21; LiteLLM says enterprise customers on its private registry were not affected)

### The failure
- `root_cause`: credential-exposure (primary, per LiteLLM's account: an agent wrote a secret it held into traffic that was logged). Contributing: operator-error (the internal deployment was "exposed to the public internet", response bodies were being logged, and per The Hacker News LiteLLM had on 19 October temporarily widened release permissions for two engineers), and supply-chain-compromise (the downstream event the stolen tokens enabled)
- `failure_locus`: harness (the Claude Code client as the point where the token entered a response body, per LiteLLM; because the mechanism is undescribed it is not known whether this sits in client code or in model output, so model-provider is the alternative reading)
- `exploitation_status`: in-wild-exploited (a real actor used the leaked tokens against a real release pipeline and shipped malware to the public package indexes)
- `mechanism`: Per LiteLLM's post and timeline, with the independent additions attributed. (1) LiteLLM developers ran Claude Code through an internal LiteLLM deployment that logged response bodies; LiteLLM says it has "observed specific situations in which Claude Code will embed a user's GitHub CLI OAuth token into a response body", so tokens appeared in that deployment's logs. (2) The deployment "was exposed to the public internet"; LiteLLM found "an unexpected, innocuously named user account" in it and believes "the attacker gained access to this deployment, obtained the GitHub CLI OAuth tokens from its logs, and subsequently used those credentials to compromise our release workflow". How the attacker got in is "not yet confirmed"; LiteLLM suspects "a recently patched vulnerability". (3) On 2026-10-21 at 10:08:29 UTC GitHub branch protection rejected an unauthorized change to the private release workflow; five seconds later "a credential associated with a privileged developer account was used to override those protections" and apply the change. (4) At 10:46 the modified workflow ran against an attacker-controlled lookalike repository, `Berri-AI/litellm` (the real one is `BerriAI/litellm`), so the poisoned build was signed and published through the official pipeline; a second developer's credential satisfied the production approval gate at 11:11. (5) Seven malicious `litellm==1.107.0` wheels went to PyPI at 11:39:51 to 11:40:13 UTC; container jobs published compromised images at 11:46:56. The official 1.107.0 source tag did not contain the malicious files. (6) At 11:53 a third developer's credentials were used to delete the production and staging workflow records, which "limited the workflow logs available for investigation". (7) The payload, per LiteLLM and The Hacker News: a `cook.pth` file that runs a credential-stealing routine on any Python start (system, browser, developer, cloud and AI-tool secrets, exfiltrated to a lookalike domain), a `sitecustomize.py` that fetches a second-stage domain, and a detached daemon that polls for a command-and-control domain and runs remote Python, making the package a remote-access trojan. (8) Wiz reports that from 16:20 to 17:01 UTC the attacker validated AWS instance-role credentials harvested from compromised CI runners and Kubernetes nodes with `sts:GetCallerIdentity` followed by Bedrock model-listing calls, "consistent with LLMjacking", about 4.5 hours after exfiltration. (9) The workflow was restored by 12:24, PyPI removed the package by 13:23, and all Docker Hub tags were removed or repointed by 14:20 UTC. The agent-side step (1) is the reason this event is in the registry; steps (3) to (9) are an ordinary human-run supply-chain attack and would be out of scope on their own
- `adversary_present`: yes (for the exploitation; the token disclosure itself, as described, involved no adversary)

### Impact
- `severity`: loss (malware was live on the public indexes for roughly two hours and installed; Wiz observed stolen AWS credentials being validated; downstream users were told to assume exfiltration succeeded, rebuild hosts and rotate every reachable secret)
- `direct_loss_usd`: unknown (no figure published by LiteLLM or any downstream victim)
- `indirect_loss_usd`: unknown (incident response at LiteLLM; host rebuilds and credential rotation at an unpublished number of downstream installations)
- `downtime`: none reported at LiteLLM; affected downstream hosts were advised to rebuild from scratch
- `data_exposure`: three sets of LiteLLM developers' GitHub CLI OAuth tokens, including an organisation owner's (LiteLLM). Downstream, on hosts that installed 1.107.0 with outbound internet: browser, developer, cloud and AI-tool secrets per The Hacker News, and AWS instance-role credentials from CI runners and Kubernetes nodes per Wiz. Counts of affected installs are not published

### Detection and recovery
- `detected_by`: operator (LiteLLM's timeline has the unauthorized workflow revision removed at 12:09 UTC, about 30 minutes after upload, and the post does not name an outside reporter; SafeDep, Socket, StepSecurity, Upwind and Wiz published analyses the same day, per The Hacker News and Wiz)
- `time_to_detect`: about 30 minutes from the first malicious upload to the start of workflow restoration (LiteLLM timeline). The token exposure in the gateway logs was not detected until the post-incident investigation; its duration is not published
- `time_to_recover`: PyPI clean by 13:23 UTC (1 h 43 min after upload); Docker Hub and GHCR clean by 14:20 UTC (2 h 34 min)
- `remediation`: compromised packages removed from PyPI and the container registries; maintainer credentials "revoked ... to minimal necessary"; users told to pin 1.106.2 or an earlier explicit version, delete `cook.pth` and `sitecustomize.py`, kill the loader daemon, prefer rebuilding hosts, rotate instance IAM roles, provider keys in the proxy database, master and virtual keys and the database password, and check CloudTrail for `GetCallerIdentity` from the instance role (LiteLLM)
- `structural_fix`: none stated at the time of drafting; LiteLLM's post says more details will follow. Context from The Hacker News: after the March 2026 compromise LiteLLM moved releases to a private repository, made Docker tags immutable and signed images, and the 19 October temporary widening of release permissions undercut part of that
- `controls_that_worked`: GitHub branch protection rejected the first unauthorized workflow change (10:08:29 UTC) and was only overcome with an organisation owner's token; enterprise customers on LiteLLM's private registry were unaffected; the public indexes pulled the artifacts within about two hours
